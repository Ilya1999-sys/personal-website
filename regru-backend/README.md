# Перенос портфолио на виртуальный хостинг REG.RU

Пакет использует текущую статическую вёрстку, PHP для API админки и MySQL для хранения кейсов/категорий. PHP-источник лежит отдельно и не публикуется как файлы сайта на Cloudflare Pages.

## Подготовить перенос данных

Если в облачной админке есть изменения, которых нет в `content/cases.json`, сначала экспортируйте актуальные кейсы и категории с работающего Cloudflare Pages, включая загруженные в R2 изображения:

```sh
node scripts/export-cloudflare-data.mjs
```

По умолчанию скрипт берёт `https://ilya-polikarpov-portfolio.pages.dev`. Можно передать другой URL первым аргументом. Если экспорта нет, сборщик возьмёт checked-in кейсы из `content/cases.json` и стандартные категории. После этого соберите папку для загрузки:

```sh
node scripts/package-regru.mjs
```

Результат появится в `website/regru-dist`. Экспорт Cloudflare нужен только для переноса более новых данных из облачной админки; иначе используется Git-версия содержимого.

## Автоматически публиковать изменения на REG.RU

Workflow `.github/workflows/deploy-regru.yml` собирает сайт и публикует его на хостинг после каждого push в `main`. Базу MySQL, PHP-конфигурацию с паролями и изображения из админки он не заменяет и не удаляет.

Перед первым push с workflow добавьте параметры в GitHub: `Settings → Secrets and variables → Actions`.

**Repository secrets** (значения доступны только workflow):

- `REGRU_FTP_SERVER` — адрес FTP-сервера из панели REG.RU;
- `REGRU_FTP_USERNAME` — FTP-логин;
- `REGRU_FTP_PASSWORD` — FTP-пароль.

**Repository variables**:

- `REGRU_FTP_PROTOCOL` — `ftps`, если этот протокол доступен на хостинге; иначе протокол, указанный REG.RU (`ftp` или `ftps-legacy`). Обычный `ftp` передаёт пароль без шифрования;
- `REGRU_FTP_PORT` — порт из панели REG.RU (часто `21`, но используйте значение своего подключения);
- `REGRU_FTP_SERVER_DIR` — каталог сайта, куда вручную загружали содержимое `regru-dist`. Путь зависит от FTP-корня аккаунта. Укажите его со слешем в конце.

Не отправляйте FTP-пароль в чат и не добавляйте его в файлы проекта. Каждый push в `main` автоматически публикует сайт. Ручной запуск workflow по умолчанию работает в режиме предпросмотра (`dry_run = true`); реальную публикацию можно запустить вручную, выбрав `dry_run = false`.

Сборщик готовит пакет из файлов в Git и при отсутствии локальной миграционной выгрузки использует `content/cases.json` только как файл первоначального наполнения. `api/initial-data.json` не публикуется, поэтому существующая база и изменения кейсов через админку сохраняются. `api/config.php` и `uploads/cases/` исключены из публикации и синхронизации.

## Подготовить REG.RU

1. Закажите Linux-виртуальный хостинг с PHP и MySQL (не Host-Lite). Выберите домен `ilyapolikarpov.ru`.
2. Создайте базу MySQL и пользователя в панели REG.RU. Сохраните имя базы, пользователя, пароль и адрес MySQL.
3. В распакованной папке переименуйте `api/config.example.php` в `api/config.php` и внесите данные базы.
4. Сгенерируйте хеш нового пароля админки на своём компьютере:

   ```sh
   php -r 'echo password_hash("ВАШ_НОВЫЙ_ПАРОЛЬ", PASSWORD_DEFAULT), PHP_EOL;'
   ```

   Вставьте результат в `admin_password_hash` в `api/config.php`. Не отправляйте пароль/конфигурацию в чат и не добавляйте `config.php` в Git.
5. Через FTP/SFTP или файловый менеджер загрузите **содержимое** `regru-dist` в корневую папку сайта. Проверьте, что хостинг исполняет PHP и разрешает `.htaccess`/`mod_rewrite`; файл `.htaccess` направляет `/api/*` и `/admin/*` в PHP-роутер.
6. Включите HTTPS-сертификат в панели REG.RU. Сессия админки использует защищённую cookie и должна работать по HTTPS.

Таблицы MySQL и начальные записи создаются при первом обращении к `/api/cases` или `/api/categories`. Для этого MySQL-пользователю нужно разрешение создавать таблицы. Обложки, которые администратор загружает после переноса, сохраняются в `uploads/cases`; папке нужно дать PHP право записи.

## Вход в админку через Google и пароль

Админка теперь закрыта на сервере: до подтверждения Google-аккаунта запросы к `/admin/` возвращают страницу «Страница недоступна», а административный API отвечает `403`. После входа с подтверждённым адресом `iliyapolikarpov@gmail.com` показывается существующая форма пароля. Вход Google действует 12 часов; пароль остаётся отдельным вторым шагом.

1. В [Google Auth Platform](https://console.cloud.google.com/auth/clients) создайте OAuth-клиент типа **Web application**. В **Authorized redirect URIs** укажите ровно `https://ilyapolikarpov.ru/api/admin/google/callback`. Для серверного потока JavaScript origin не требуется.
2. Настройте экран согласия. Если приложение находится в режиме **Testing**, добавьте `iliyapolikarpov@gmail.com` в список тестовых пользователей.
3. В файловом менеджере REG.RU откройте `~/www/ilyapolikarpov.ru/api/config.php` и добавьте в возвращаемый массив три строки из `config.example.php`: `google_client_id`, `google_client_secret`, `google_admin_email`. В первые две вставьте значения созданного OAuth-клиента; адрес оставьте `iliyapolikarpov@gmail.com`. Не присылайте Client Secret в чат и не помещайте `config.php` в Git.
4. Убедитесь, что на хостинге есть PHP cURL и исходящее HTTPS-соединение к Google. Затем опубликуйте эту версию сайта и откройте `/admin/` в приватном окне. До входа должен быть код `403` и ссылка «Войти через Google», после входа нужным аккаунтом — форма пароля. Другой аккаунт должен получать `403`.

Пока поля Google не заполнены, `/admin/` отвечает `503` и не показывает форму пароля. Поэтому подготовьте OAuth-клиент и `api/config.php` **до** публикации этой версии. Публичные страницы при этом продолжают работать.

## Страницы кейсов через админку

В `/admin/` у карточки можно выбрать внешнюю ссылку или отдельную страницу по адресу `/cases/имя-кейса/`. Страница содержит заголовок, описание и одну общую задачу либо несколько именованных задач. В каждой задаче редактируются проблема, задача, процесс работы, подзадачи с изображениями и кнопками, а также итог. Для галереи выбирают 3 или 4 колонки на больших экранах; остальные размеры определяет адаптивная вёрстка. Изображения JPG, PNG и WebP до 10 МБ загружаются через админку в `uploads/cases/` и не перезаписываются деплоем.

При первом запуске новой версии PHP добавит столбец `detail_json` и заполнит две уже готовые страницы их текущим содержимым. Пользователю MySQL нужны права на `ALTER TABLE`. После миграции содержимое страниц редактируется в базе, а push в `main` обновляет только шаблон и стили.

## Важные ограничения переноса

- Текущий интерфейс остаётся тем же. Серверная часть Cloudflare заменяется PHP/MySQL.
- До смены DNS откройте копию на техническом адресе REG.RU и проверьте главную, фильтры и `/admin/`. Только затем переключайте DNS домена на хостинг.
- Веб-хостинг оплачивается отдельно от продления домена. При отказе от Cloudflare DNS оставьте DNS у REG.RU либо создайте там записи, указывающие на IP из панели хостинга.
- Не удаляйте текущий проект Cloudflare, пока проверка и перенос данных не завершены: он остаётся резервной версией.
